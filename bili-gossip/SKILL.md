# 深度吃瓜

通过公开网页搜索生成可溯源、可降级的HTML报告，并聚合可公开访问的B站视频。

## 工作流

1. 识别用户输入中的人物名、事件名和关系词。只有一个明星姓名时，默认生成人物近况与关键前情复盘；出现两个姓名时，默认生成双方关系、公开互动与近期触发点复盘；出现三个及以上姓名时，围绕共同事件梳理核心当事人、回应者、关联者和背景人物，不把所有人机械地两两组合。姓名可由`&`、`和`、`与`、`×`、空格或顿号连接，不要求用户额外写"关系"或"复盘"。

   同时整理检索词集合，用于后续各步骤：
   - **事件核心词**：用户输入的事件描述词（权重×3）
   - **花名/CP名**：艺人常用外号、粉丝叫法、CP合称（权重×2）
   - **别名/拼音变体**：英文名、缩写、拼音（权重×1）

2. **并行启动5个数据源采集任务**（同时发出，不等待前序完成）：

   ```
   ├─ 源1: B站搜索  — 使用「事件核心词 + 花名 + CP名 + 拼音变体」检索视频列表（top 30）
   ├─ 源2: B站弹幕  — 聚合事件相关视频的高频弹幕词云
   ├─ 源3: 网页搜索 — 检索最近30天的事件相关报道，分别搜索「核心人物/事件」「最近为什么又被讨论」「官方回应」「事件日期/进展」
   ├─ 源4: UP主元数据 — 提取候选视频的UP主基础信息，用于信源标注
   └─ 源5: B站热搜/趋势 — 判断事件是否在热点周期内（用于新瓜/旧瓜角标判断）
   ```

   等待全部返回后统一去重汇总，再进入后续步骤。打开候选原文，不直接采用搜索结果摘要。按官方一手声明、权威媒体、正规门户的顺序收集事实；微博智搜、抖音求真卡仅作补充。为每个来源记录名称、原文URL和来源类型。

3. 普通事实节点至少需要两个不同域名的独立来源相互印证；官方机构、当事人或工作室的一手声明标记为`is_primary: true`后可单独作为节点。

4. 生成不超过6个、按日期正序排列的时间线节点，删除无法确认的说法。选点时优先解释本轮话题触发点，再补充与它关系最强的起点、转折和必要背景；不要按年份、固定时间窗口或新旧节点比例机械凑数。省流版和时间线的写作风格见[各板块写作指引](#各板块写作指引)。

5. **报告卡采用7板块Schema骨架，每个板块独立并行填充，互不依赖，最后顺序拼装**：

   ```json
   {
     "sections": [
       {"id": "summary",   "title": "省流版",         "status": "required"},
       {"id": "timeline",  "title": "事情是这样的",    "status": "required"},
       {"id": "viewpoint", "title": "观点阵营",        "status": "required"},
       {"id": "danmaku",   "title": "弹幕神了",        "status": "required"},
       {"id": "memory",    "title": "互联网有记忆哦",  "status": "required"},
       {"id": "extend",    "title": "来阿B补课",       "status": "required"},
       {"id": "install",   "title": "安装指引",        "status": "required"}
     ]
   }
   ```

   **所有板块骨架必须占位，数据不足时输出对应兜底文案，绝不跳过板块**。各板块兜底文案见[产品规则](references/product-rules.md)。

6. **视频筛选**（配合步骤2源1的采集结果）：

   对每条候选视频按以下规则计算关联分数：
   ```
   score += 3  如果 事件核心词 出现在标题/简介中
   score += 2  如果 花名或CP名 出现在标题/简介中
   score += 1  如果 别名或拼音变体 出现在标题/简介中
   ```

   **硬过滤**（满足任一条件且不含事件核心词，直接排除）：
   - 标题含"甜向""高甜""撒糖""纯BGM""混剪"等标签
   - 纯CP二创、与本次事件无关的非事件向内容
   - 播放量低于30万或时长短于2分钟（数据明确时）

   **考古/补课互斥规则**：
   - "互联网有记忆哦"（考古）使用 Query = 事件核心词 + 深度解读/历史追溯/过往物料
   - "来阿B补课"（延展）使用 Query = 事件核心词 + 相关艺人最新动态/相关事件方
   - 两个板块的搜索Query强制不重叠；考古已抓取的视频bvid，补课自动排除

   打开视频页核对真实`bvid`、标题、UP主、链接及可见播放量/时长，优先记录公开页面中的封面URL（`og:image`）。

7. 不生成弹幕原文、观点阵营内容或精确视频时间戳。公开视频只能作为整条视频入口；无法确认播放量或时长时保留警告，不声称已经满足内部准入门槛。

8. 按[产品规则](references/product-rules.md)和[报告数据契约](references/report-contract.md)组织JSON。将Agent生成的JSON写入文件。若视频卡缺少封面，先从B站公开视频页的`og:image`公开元数据补齐：

```bash
python scripts/enrich_public_video_metadata.py --input <report.json> --output <enriched-report.json>
```

检查命令输出的`warnings`。封面请求失败时保留空值并继续，不删除已合格的视频，也不使用登录态、Cookie或页面截图伪造封面。再运行公开Web版准备脚本：

```bash
python scripts/prepare_web_only.py --input <enriched-report.json> --output <web-only-report.json>
```

检查命令输出的`warnings`。被删除的事实或视频不得补写；若时间线为空，使用全局兜底。

9. 渲染公开Web版JSON：

```bash
python scripts/render_report.py --input <web-only-report.json>
```

10. 将脚本输出的HTML路径返回给用户。

## 检索预算

- **网页信息采集总时限为5分钟**。所有需要打开的网页（事实信源页、B站视频页）必须并行发起请求，不得串行等待。5分钟到时未返回的请求直接放弃，已获取的数据继续生成报告，不等待超时请求补充。
- 一份常规报告默认打开约8至15个不同网页：5至8个事实信源页、3至6个B站视频页；同一原文可支持多个时间线节点，不重复打开。
- 同一事实达到双信源要求后停止扩张检索；优先补齐缺少交叉验证的节点，不为增加网页数量重复搜索相同结论。
- 时间线最多使用6个节点，直接相关视频最多3条，延展视频最多3条。只有信源冲突、原文失效或关键事实缺口时才突破默认预算。
- 播放量、时长、封面等可通过公开元数据请求核对时，不额外打开浏览器页面。封面优先使用公开页`og:image`并转成`https`原图URL；请求失败时保留警告和封面占位，不无限重试。

## 各板块写作指引

**「省流版」**

- System角色："你是B站百大UP主@吃瓜bot，正在录制新视频的开场白。你了解B站用户喜欢什么：炸裂的、有争议的、让人想一键三连的内容。"
- 叙事原则：客观事实 + 标题党语气。不说"XX塌房实锤"，说"看完这5个细节你还站XX吗？"
- 长度规则：不设字数上限。底线：说清5W（谁/什么事/何时/为何/怎么引起关注）。省略号只用一次——打在读者最想往下看的那个地方。
- 多角度：根据事件类型自动选2-3个维度展开（可选：争议角度/CP角度/时间线对比/行业内幕/粉丝反应），不一致的维度并列呈现。

**「观点阵营」**

- System角色："你是两方吃瓜群众的嘴替。你的任务不是客观，是让正反方各说一句最能刺痛对方的话。"
- 生成规则：
  - 正方：找出1个最尖锐的支持理由（要让人看完觉得"有道理"）
  - 反方：找出1个最尖锐的反对理由（要让人看完觉得"好像也对"）
  - 如果双方太温和 → 二次改写，增加交锋感
- 缺失处理：数据再少也强制输出，标注"样本有限"。不暴露具体采集数量。

**「事情是这样的」**

- System角色："你是说书人，不是新闻纪录员。你的任务是把这件事讲成一个有起承转合的故事，每个节点是剧情推进，不是事实播报。"
- **不记流水账**：不要把所有事件列出来，找那一个最有力的细节，一个细节顶10条事件。
- **活人感**：大胆直接引用当事人的真实语言——他/她发了什么微博、说了什么话、做了什么动作，比"工作室发表声明"有力100倍。
- **画面感**：写读者能在脑子里播放的场景。"当天被拍到独自开工、全程单身状态"比"当事人否认恋情"有画面感。
- 用动词选词暗示张力："悄悄删帖"不是"删除了帖子"，"连夜发声"不是"发表声明"，"斩断烂桃花"不是"结束关系"。
- 节点之间要有因果钩子，转折点用更强烈的措辞标出。
- 信息源面向用户不展示具体名称和链接，内部保留引用用于校验，生成时统一用"综合多方信息/据公开报道"表述。

**对照示例（干燥版 vs 说书版）：**

> 干燥版：2024年3月，工作室发表声明否认恋情，称二人只是普通朋友关系。
> 说书版：绯闻爆出的第二天，工作室发来五行声明——通篇没有一个字提对方名字，只说"正常工作往来"。评论区第一条高赞：这种声明，否认的不是恋情，是恋情里的那个人。

> 干燥版：双方此前曾在多个场合公开互动，引发外界关注。
> 说书版：活动上刻意躲开、零对视装作陌生人，转头花絮里两个人又偷偷对视拉扯——这套流程，粉丝见过太多次了。

## 豆包与元宝

- 默认不操作豆包或元宝，优先使用Agent自带Web搜索。
- 只有用户明确要求且浏览器已登录时，才可临时操作其网页；不得索取或保存账号密码、Cookie或验证码。
- 将豆包/元宝输出只作为检索线索，不作为最终信源。必须打开其引用的原始网页并按双信源规则重新验证。
- 页面要求登录、出现验证码或无法稳定读取时立即跳过，不影响主流程。

## 内容边界

- 将"已确认事实""UP主观点""评论/弹幕情绪"分别标注，不混写。
- 不使用"实锤、真相、故意、内幕"等超出证据的定性词。
- 不把搜索结果摘要本身当作最终证据；尽可能打开原文核对标题、日期和正文。
- 数据未达到门槛时输出对应兜底文案，不直接隐藏板块骨架。全局信息不足时使用运营兜底文案。
- 所有视频卡必须绑定真实`bvid`和B站视频链接。能从公开页面获取封面时必须写入`cover`并展示；获取失败时允许使用模板占位。公开Web版不展示精确时间戳。
- 弹幕模块和观点阵营模块固定隐藏，不能把新闻评论、搜索摘要或豆包/元宝结论伪装成B站弹幕或观点数据。

## 安装口令

```shell
npx skills add https://github.com/jiubanszd/bili-gossip-skill/tree/main/bili-gossip -g -y
```

报告页面默认展示并复制这条跨Agent安装口令；如需分发其他仓库版本，可通过`BILI_SKILL_INSTALL_COMMAND`临时覆盖。
